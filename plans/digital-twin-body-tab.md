# Digital Twin Body Model Tab Plan

## Objective

Add a dedicated **Machine Body** tab inside the existing `/digital` page and display `C:\FPT\3D\STEP\Body.glb` there as a standalone model. The model will sit on a simple display plane with a fixed showcase camera. The existing animated mechanism remains available in its own tab. These models are intended to become parts of one machine later, but this increment must not align, overlay, merge, or imply that they are already assembled.

This is a plan-only artifact. It does not authorize copying the model or changing product code. Implementation begins only after a separate user instruction.

## Confirmed decisions

- **Placement:** add an in-page tab named “Machine Body” (localized EN/VI) to the existing `/digital` experience; do not add a new URL or open a browser tab.
- **Current model relationship:** keep the mechanism assembly and `Body.glb` as separate views. Do not combine, spatially align, or edit either asset in this increment. Plan that integration separately after the machine clusters and coordinate frames are ready.
- **Rendering architecture:** keep the existing Next.js, React Three Fiber, and Three.js stack. Keep the mechanism assembly API and its tested motion module unchanged. Give the body model a feature-owned viewer and local GLB loader.
- **Scene UX:** the Body tab shows only `Body.glb`, grounded on a simple plane/table-like stage. Its camera orientation is fixed; rotate and pan are disabled. Zoom and camera reset remain available.
- **Tab lifecycle:** only the selected model viewer is mounted, so the page never holds two active WebGL canvases. Returning to a tab may reload/reinitialize that view; automatic mechanism motion must return stopped, as it does by default today.
- **Data boundary:** local static model assets and browser-only view state; no Backend, API, telemetry, IoT, MQTT, or physical-machine commands.
- **Execution preference:** Standard, TDD Off was previously selected for this Digital Twin work. TDD Off does not waive post-change verification. No implementation is authorized by this plan request.

## Decision record

| Decision | Options considered | Selected and rationale |
| --- | --- | --- |
| Where to expose Body.glb | In-page tab under `/digital`; separate `/digital/body` route; separate browser tab | In-page tab. It keeps the shared Dashboard shell and makes the current mechanism and new body easy to switch between without creating another navigation destination. |
| Whether to combine assets now | Display the body alone in a separate tab; overlay/align it with the mechanism; merge/export a combined GLB | Separate body-only view now. No shared placement has been approved or verified, and combining now would risk hiding or disrupting the existing motion setup. Future assembly is explicitly deferred. |
| Scene/render lifecycle | Two simultaneously mounted canvases; one active viewer at a time | Mount only the active viewer. This bounds WebGL/GPU resources and keeps the existing assembly module's ownership intact. The trade-off is that switching back reinitializes that viewer; model motion must restart stopped. |
| Model asset handling | Modify the source file; copy it into the app's static asset tree | Copy the source file unchanged into a feature-specific public asset path. This is reversible and preserves the original CAD export. |

## Current-state findings and assumptions

- `/digital` currently renders `DigitalTwinViewer` from `src/app/(dashboard)/digital/page.tsx`.
- `DigitalTwinViewer` owns the current assembly controls and mounts `DigitalTwinCanvas`; the Canvas uses the Dashboard's installed React Three Fiber/Three.js versions. The assembly factory returns a `THREE.Group` and owns its existing model loading and motion contract.
- The current assembly has 13 local GLB assets under `public/models/digital-twin/cluster-01/` (2,113,712 bytes). It uses the local Draco decoder at `/draco-gltf/`.
- Read-only inspection found `C:\FPT\3D\STEP\Body.glb` at 378,480 bytes. It is a GLB 2.0 file generated by SOLIDWORKSGLTF, contains 52 meshes and one unnamed material, and declares `KHR_draco_mesh_compression` as required. The asset is not yet copied into the Dashboard.
- The GLB metadata alone does not establish its final visual orientation, floor contact point, or spatial relationship to the mechanism. Phase 1/2 must inspect these in the browser. A feature-owned display transform may be applied without modifying the source GLB; no transform may be used to align it to the mechanism in this increment.
- Existing `DigitalTwinViewer` currently has its own page heading and full OrbitControls. The workspace/tab owner will provide the shared heading and tab semantics; body-only fixed-camera behavior must not silently change the mechanism tab's existing controls.
- The earlier `plans/digital-twin-model-integration.md` records Phase 3 as Partial and Phase 4 as Unverified because some runtime checks were unavailable. This new plan does not change or claim completion of those findings.
- The repository has no test script/framework in `package.json`; use targeted asset/contract checks, TypeScript/build, and browser evidence unless a suitable existing test harness is found during implementation.

```text
public/models/digital-twin/cluster-01/                # current local assembly assets

```

Planned additions/adjustments:

```text
src/app/(dashboard)/digital/page.tsx               # compose DigitalTwinWorkspace
src/components/features/digital-twin/
  DigitalTwinWorkspace.tsx                           # shared heading, tab state, active panel
  DigitalTwinViewer.tsx                              # retain as the existing mechanism panel
  BodyModelViewer.tsx                                 # Body loading/error/status and camera controls
  BodyModelCanvas.tsx                                 # Body GLB scene, display plane, fixed camera
  DigitalTwinCanvas.tsx                               # unchanged mechanism camera behavior
  assembly/                                          # unchanged motion/assembly API
src/lib/i18n/translations.ts                         # EN/VI labels and state messages for tabs/body
public/models/digital-twin/body/Body.glb              # copied source asset, unchanged
```

`DigitalTwinWorkspace` owns navigation between the two model views and mounts only the selected panel. `BodyModelViewer` owns the Body tab's UI states and reset/zoom actions. `BodyModelCanvas` owns the static GLB load lifecycle and its R3F scene. The existing assembly remains feature-owned by `DigitalTwinViewer` and its current assembly module. The route composes the feature; it does not contain Three.js or loading logic. No shared UI, data adapter, new route, or speculative general-purpose model registry is introduced.

## Out of scope

- Co-locating or aligning `Body.glb` with the mechanism assembly, or claiming they are currently assembled.
- Editing, recompressing, simplifying, renaming nodes in, or re-exporting the source GLB.
- Adding the remaining mechanical clusters or creating a generalized multi-machine framework.
- Adding a cutaway, transparent shell, internal-animation controls, or motion to the Body tab.
- Changing the existing assembly module's motion, controls, camera, assets, or Backend/data boundaries except for the minimum page composition needed to put it in its tab.
- Backend/API, IoT, telemetry, persistence, auth, physical equipment control, or coffee-flow UI.
- Updating or closing the existing integration plan's Phase 3/4 verification gaps.

## Phase 1 — Stage and validate the Body asset

**Outcome:** the Dashboard has a verified local copy of the Body GLB at `public/models/digital-twin/body/Body.glb`, with the source file left unchanged.

**Scope:** re-check that the source file exists and record its size/hash at execution time; copy it byte-for-byte into the feature-owned public asset directory; inspect its GLB header/JSON and required extensions; confirm its node/mesh/material inventory and Draco requirement. Check that the app's installed GLTFLoader/DRACOLoader versions and local decoder path can support this file. Do not assume that Draco compatibility is proven solely by the existing assembly's assets.

**Not in scope:** viewer/page changes, geometry modification, compression/optimization, mechanism alignment, or copying any other CAD files.

**Dependencies:** source file is readable at `C:\FPT\3D\STEP\Body.glb`; implementation has been separately authorized.

**Implementation boundary / affected components:** only `public/models/digital-twin/body/Body.glb`. Read loader/decoder configuration for compatibility; do not change shared decoder assets unless an observed incompatibility requires a separate user-approved change.

**Side effects:** adds approximately 378,480 bytes (about 0.361 MiB) to local static assets and deployment payload. The source path remains untouched.

**Verification:** compare source and destination hashes and byte counts; parse the GLB 2.0 header/JSON; confirm `KHR_draco_mesh_compression` requirements and all referenced buffers; verify the configured decoder is local and compatible; record the final asset footprint. If feasible without a product UI change, use an existing loader/browser harness for a decode smoke check; do not claim browser rendering until Phase 2 evidence.

**Acceptance criteria:** the target asset is byte-identical to the source snapshot, structurally valid, and its decoder requirements are satisfiable from the existing local app setup; no source file or unrelated asset is changed.

**Entry condition:** separate user authorization to implement has been given and the source file remains available.

**Exit condition:** asset checks pass and the exact source/destination hashes, sizes, and decoder path are recorded.

**Risks and response:** the source may change, be unreadable, be corrupt, or use an unsupported Draco setup. Stop and report the evidence; do not silently substitute another file, modify the CAD export, or fetch a decoder from a CDN.

**Approval/stopping gate:** stop for user direction if the source differs materially from the inspected asset, if license/provenance concerns arise, or if a decoder/dependency change is required.

**Review gate:** read-only review confirms only the requested asset was added and the source file was not altered.

## Phase 2 — Add the separate Body tab and fixed showcase viewer

**Outcome:** `/digital` contains two accessible model tabs. “Machine Body” opens a standalone view of `Body.glb`; the existing mechanism remains available separately and is not overlaid or aligned with it.

**Scope:** add `DigitalTwinWorkspace` as the route-level feature composition. Provide “Cụm cơ khí / Mechanism” and “Thân máy / Machine Body” tabs in EN/VI. Make “Machine Body” the initial tab so the requested asset is immediately visible; clicking the mechanism tab continues to show the existing assembly viewer. Mount only the active viewer and ensure switching away unmounts it cleanly; when the mechanism viewer is reopened, automatic motion remains stopped by default.

For the Body view, add a client-only `BodyModelViewer` and feature-owned `BodyModelCanvas`. Load the same-origin GLB with the app's installed Three.js `GLTFLoader` and local `DRACOLoader` at `/draco-gltf/`. Preserve the imported geometry and hierarchy. Inspect the rendered asset, compute/confirm its bounds, and use a feature-owned display transform only as needed to orient it for presentation, center it, and ground its lowest point on a simple plane. Set a stable fixed showcase view; disable camera rotation and panning. Retain zoom (wheel/pinch and/or accessible buttons) and a reset-to-default-framing control. Provide independent loading, ready, and recoverable error/retry states for this tab. Keep model readiness/error boundaries local so a Body load failure does not corrupt the mechanism tab.

**Not in scope:** rendering both models together, matching their coordinates, editing their source geometry, or implementing internal mechanism motion in the Body view.

**Dependencies:** Phase 1 passes; route remains under the existing Dashboard shell; installed dependencies remain the app's current Three.js/R3F stack.

**Implementation boundary / affected components:**

- `src/app/(dashboard)/digital/page.tsx`: import/compose `DigitalTwinWorkspace` only.
- `src/components/features/digital-twin/DigitalTwinWorkspace.tsx`: own tab selection, semantic tablist/tab/tabpanel behavior, shared page heading, and active-view mounting.
- `DigitalTwinViewer.tsx`: retain the current mechanism behavior; make only minimal presentational extraction if needed to avoid duplicate headings.
- `BodyModelViewer.tsx` and `BodyModelCanvas.tsx`: own body-specific state, controls, loader lifecycle, R3F scene, stage plane, lighting, and camera fitting.
- `src/lib/i18n/translations.ts`: add all visible tab/body loading/error/reset/zoom labels in both supported languages.
- `public/models/digital-twin/body/Body.glb`: consume the Phase 1 local asset.
- Do not import assembly internals into the body viewer or move feature behavior into generic Dashboard components.

**Side effects:** adds client-side tab state and one extra model asset. Only one WebGL Canvas is mounted at a time, avoiding simultaneous context/GPU allocation. Switching tabs tears down the inactive viewer; returning to it may reload/reinitialize model state. All new strings are localized; no network dependency beyond same-origin static assets is added.

**Verification:** run TypeScript and production build; inspect the route tree for one `/digital` page; in a browser verify initial Body tab, local Draco decode and visible geometry, stage contact/orientation/framing, zoom/reset, disabled rotate/pan, error/retry, tab switching and safe unmount/remount, default-stopped mechanism motion, keyboard tab navigation/focus, EN/VI strings, and narrow viewport behavior. Inspect console/network for failed assets, external decoder/model requests, or BE/telemetry requests.

**Acceptance criteria:**

- `/digital` remains inside the standard Dashboard shell and uses an in-page tablist rather than a new route/browser tab.
- Body is the initial selected tab and shows only the standalone `Body.glb` on its stage; the mechanism is never visible in the Body panel.
- The model is properly grounded and framed after visual inspection; no asset source transform is rewritten.
- Rotate and pan cannot change the Body camera orientation; zoom and reset work and are understandable/accessible.
- The mechanism tab still loads and exposes its existing controls; it is not combined with the Body and starts with automatic motion stopped after remount.
- Loading/error/retry states are recoverable, tabs are keyboard-operable and localized, and only one viewer Canvas is mounted at a time.
- No BE/IoT/live-state integration or external model/decoder fetch is introduced.

**Entry condition:** Phase 1 passed its review gate; the existing route and assembly viewer are re-read before editing so intervening user changes are preserved.

**Exit condition:** both tabs work in the browser and all acceptance criteria have repeatable evidence; any unverified browser/runtime requirement is explicitly recorded rather than inferred from source inspection.

**Risks and response:** the GLB may have unexpected up-axis, scale, pivot, or visual composition; determine display-only transforms from the loaded asset and stop if the intended view requires editing source geometry. Hidden/transparent surfaces are not part of this plan. Context loss or asynchronous completion after tab unmount must be safely handled. Do not upgrade Three.js or alter the assembly API to make this view work without a separate decision.

**Approval/stopping gate:** stop if the asset cannot render with the local decoder, if the camera orientation needed to show it is materially different from the fixed showcase direction, if preserving the current mechanism requires combining the models, or if any work would modify the source assembly contract.

**Review gate:** read-only review checks route ownership, active-view lifecycle, decoder locality, absence of model composition, accessible tab/camera controls, EN/VI coverage, and no changes to assembly motion behavior.

**Not in scope:** fixing unrelated Dashboard lint/build warnings, expanding into other model clusters, or resolving prior-plan verification gaps unrelated to this tab.

**Dependencies:** Phase 2 implementation is complete and its review gate passed; browser and build environment are available.

**Implementation boundary / affected components:** verification only across the Phase 1/2 files. Product defects return to the phase that owns them. No unrelated user changes are reverted or overwritten.

**Side effects:** build/test caches may be generated; do not remove unrelated data. No commit, publish, deployment, or external communication is authorized.

**Verification:** record commands and exit codes, browser/viewport/input method, asset/decoder requests, visual results, keyboard/touch behavior, EN/VI behavior, and cleanup after tab switching. Re-run `git diff --check`; inspect the final diff to ensure no unrelated files or source CAD files changed. If the repo lint script remains unsupported under its current Next.js version, record it without broad tooling changes.

**Acceptance criteria:** TypeScript and production build pass; browser shows the standalone body and the existing mechanism in separate tabs; all fixed-camera, stage, keyboard, language, error/retry, and active-view lifecycle checks pass or are explicitly marked unverified; final review confirms no composition, backend work, or unrelated modifications.

**Entry condition:** Phase 2 exit criteria are met, or the user explicitly accepts named verification gaps.

**Exit condition:** evidence and remaining limitations are recorded; no in-scope high-severity issue remains. The plan remains only a visual-model milestone and does not claim that the full machine is assembled.

**Risks and response:** an unavailable browser feature or test harness may leave runtime behavior unverified. Record exact evidence and nearest safe substitute; do not convert source review into a runtime pass.

**Approval/stopping gate:** stop and report required-check failures that need a dependency upgrade, source-model modification, new test infrastructure, or broader Dashboard work.

**Review gate:** final read-only review confirms the Body is standalone, source asset provenance is preserved, existing assembly remains separate, local-only data boundaries hold, and deferred integration is clearly handed off.
